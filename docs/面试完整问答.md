# MES-dome 完整面试问答

> 配套项目：基于 Spring Boot 4 + Vue3 的车间 MES 精简版。  
> 建议用法：先背「一句话 + 主链路 + 三层防重」，再按模块过深挖题。  
> 另见：`docs/面试讲稿.md`（短提纲）、`README.md`（启动与演示）。

---

## 一、项目总览

### Q1. 用一分钟介绍这个项目

**答：**  
这是一个面向面试的制造执行系统（MES）精简版，核心是跑通车间执行主链路：

**ERP Mock 推单 → 工单 7 态状态机 → 主动派工 → 扫码报工（RocketMQ 异步）→ 自动完工 → 回传 ERP。**

我重点手写了：工单状态机、派工与审计、报工三层防重复（Redis 幂等 + Redisson 锁 + MQ/DB 幂等）、以及 IntegrationLog 对账重试。前端用 Vue3 做了管理端和工人终端，方便演示闭环。

简历一句话：

> 基于 Spring Boot 4 + Vue3 的 MES 车间执行系统，手写工单 7 态状态机与派工审计；报工采用 Redis 幂等 + Redisson 分布式锁 + RocketMQ 异步消费防重复；MyBatis-Plus 乐观锁保证并发安全；Mock ERP 验证推单、回传与 IntegrationLog 重试闭环。

---

### Q2. 这个项目有哪些功能？

**答（按模块）：**

| 模块 | 功能 |
|------|------|
| **认证** | 登录、JWT 双令牌（access/refresh）、角色 RBAC（admin/planner/worker/qc） |
| **ERP Mock** | 推单入库并生成工序任务；关单（正常关闭/取消）；推单 Redis 幂等 |
| **工单** | 分页查询、详情（含工序）、7 态状态机、看板统计（Redis 缓存 60s） |
| **派工** | 工人列表、主动派工、派工记录 + 审计快照、工人「我的任务」 |
| **报工** | 数量/权限/状态校验；`X-Request-Id` 幂等；202 受理 + 轮询；不良原因；MQ 异步落库 |
| **状态联动** | 报工后自动流转工单状态；末工序满额自动「已完工」 |
| **集成** | ERP 回传 Topic；`integration_log` 对账；失败手动/定时重试 |
| **质检 Mock** | 报工含不良时自动生成质检任务 |
| **前端** | 管理端（工单/派工/看板/对账）；工人端（任务/报工） |
| **运维** | Docker Compose（MySQL/Redis/RocketMQ/可选 backend） |

**刻意没做（会主动说）：** 真实 SAP 对接、工单拆分合并、抢单/自动派工、离线报工、PLC 自动报工。

### Q3. 用了什么技术栈？为什么选它们？

| 层 | 技术 | 为什么 |
|----|------|--------|
| 后端 | Spring Boot **4.1** + Java 17 | 主流企业栈；SB4 需注意 aspectj、Jackson 3、Redisson 版本 |
| ORM | MyBatis-Plus 3.5 | CRUD/分页快；`@Version` 乐观锁适合报工并发 |
| DB | MySQL 8 | 事务 + 唯一键（`request_id`、`idempotent_key`）做最终幂等 |
| 缓存/锁 | Redis + **Redisson 4.6.1+** | 幂等 SET NX、看板缓存、任务级分布式锁（SB4 需 4.6+） |
| MQ | RocketMQ 5.5 原生 client | 报工异步削峰；Broker 重试 + 业务对账表 |
| 安全 | Spring Security + Auth0 java-jwt | 双令牌 + 方法级 `@PreAuthorize` |
| 前端 | Vue3 + Element Plus + Vite | 管理端/工人端双门户演示 |
| 部署 | Docker Compose | 一键起 MySQL/Redis/RocketMQ |

**面试加分一句：** 没有为了用中间件而用——Redis 解决重复提交与热点统计，MQ 解决报工同步落库的延迟和耦合，乐观锁解决同任务并发超报。

---

### Q4. 这个项目解决了什么问题？

**答（业务 + 工程）：**

1. **业务闭环问题**：ERP 计划如何落到车间执行并可回传——用 MES 承接推单、派工、报工、完工。  
2. **状态一致性问题**：工单状态不能靠人工乱点——用状态机约束非法跃迁，报工驱动自动流转。  
3. **重复报工问题**：工人连点、弱网重试、MQ 重复投递——三层幂等。  
4. **并发超报问题**：多人/连击同一工序——Redisson 锁 + 乐观锁 + 剩余数量校验。  
5. **系统集成可靠性**：回传失败怎么办——`integration_log` + 重试，而不是「发了就不管」。  
6. **可演示/可讲解**：双端 UI + 审计日志，面试能现场走主链路。

## 二、业务与领域

### Q5. MES 和 ERP 有什么区别？你项目里怎么协作？

**答：**  
- **ERP**：计划与账务侧（生产订单、库存账、成本），本项目用 Mock。  
- **MES**：车间执行侧（谁做、做了多少、质量如何）。  

协作：  
- ERP → MES：推「已释放」工单 → MES「已下发」，并生成工序任务。  
- MES → ERP：报工驱动完工后发回调 Topic，写 IntegrationLog，Mock ERP 确认。  
- ERP 关单：可映射为已关闭/已取消；若 MES 仍在执行中需冲突校验。

---

### Q6. 工单状态机有哪些状态？怎么流转？

**答：**

| code | 名称 | 典型触发 |
|------|------|----------|
| 0 | 已下发 | ERP 推单 |
| 1 | 已派工 | 首次派工 |
| 2 | 执行中 | 首次/继续报工 |
| 3 | 部分完工 | 有产出但未达计划 |
| 4 | 已完工 | **末工序报满**（自动） |
| 5 | 已关闭 | ERP/人工关闭 |
| 6 | 已取消 | ERP 取消 |

核心方法：`resolveAfterReport(current, planQty, completedQty, lastOperationDone)`。  
强调：**已完工不是按钮点出来的**，是数量 + 是否末工序算出来的；非法跃迁抛业务异常。

---

### Q7. 派工怎么做的？为什么要审计？

**答：**  
MVP 只做**主动派工**：计划员指定 `taskId` + `assigneeId`，写 `dispatch_record`，更新任务 `assigned_to`，必要时把工单从「已下发」推到「已派工」。  

审计：写 `dispatch_audit_log`（含变更快照），回答「谁、何时、把哪个任务派给了谁」。车间责任追溯是标配，面试官常问可追溯性。

工人端 `GET /api/tasks/my` 按 `priority DESC, planned_start ASC` 排序。

---

### Q8. 报工接口为什么是 202 而不是直接 200 成功？

**答：**  
报工是**异步受理**模型：  
1. API 同步校验 + 占幂等 + 插入 `production_report(status=0 处理中)` + 发 MQ；  
2. 返回 **HTTP 202** + `reportId`；  
3. 前端轮询 `GET /api/reports/{id}`，直到 status=1 成功或 2 失败。  

好处：API 快速返回，重活放 Consumer，避免把事务、状态机、回传全堆在请求线程里；也更贴近真实车间高峰。

## 三、报工防重复（高频深挖）

### Q9. 三层防重复分别防什么？少一层会怎样？

| 层 | 实现 | 防什么 | 若去掉 |
|----|------|--------|--------|
| API 幂等 | Redis `SET NX` `mes:report:idempotent:{requestId}`，Header `X-Request-Id` | 连点、前端重试 | 可能插入多条「处理中」或重复发 MQ |
| 并发控制 | Redisson `mes:lock:task:{taskId}` + MP `@Version` | 同任务并发超报 | `completed_qty` 可能超过 `plan_qty` |
| MQ/DB | Consumer 见成功单则跳过；`request_id` 唯一键 | Broker 至少一次投递 | 重复消费导致数量翻倍 |

**结论：** Redis 挡入口，锁+乐观锁挡并发，DB 唯一键+消费幂等挡消息重复——职责不同，不能互相替代。

---

### Q10. 幂等 Key 和 DB 唯一键会不会重复设计？

**答：不冲突，层次不同。**  
- Redis：短路径、快失败/快返回，TTL（如 24h），适合接口层。  
- DB UK：最终真相，消息重投、进程重启后仍有效。  

Redis 挂了仍可靠 DB；只有 DB 则接口层连点压力更大、体验差。两者一起是常见工业做法。

---

### Q11. 如果 Redis 有幂等 Key，但库被清了怎么办？

**答：**  
我们处理过「脏 Key」：`tryMark` 失败后查不到报工单，则 **release Key 再重新占坑**，避免永远卡在「报工处理中」。  
面试可补：清库要同步清 Redis，或幂等 Value 绑定 reportId 做一致性校验（项目里有 `bindReportId`）。

---

### Q12. 乐观锁和分布式锁为什么都要？

**答：**  
- **分布式锁**：缩小并发窗口，让「读剩余 → 写数量」串行化，减少无效重试。  
- **乐观锁**：最后一道防线，锁失效/超时/多实例异常时，`version` 冲突则更新行数为 0，触发重试或失败，**数据不会写坏**。  

只靠锁：锁释放后仍可能有窗口；只靠乐观锁：冲突多、体验差。组合更稳。

## 四、RocketMQ 与集成

### Q13. 为什么报工要用 MQ？同步写库不行吗？

**答：**  
同步也能写，但 MQ 带来：  
1. **削峰**：报工高峰不堵死 HTTP 线程；  
2. **解耦**：受理 vs 落库/状态机/回传分开；  
3. **重试**：消费失败 `RECONSUME_LATER`，配合业务对账。  

代价：最终一致、要幂等、要轮询状态——项目用 202 + 轮询消化。

---

### Q14. Topic 怎么划分？消息失败怎么处理？

| Topic | Tag | 用途 |
|-------|-----|------|
| `mes_report_submit` | `submit` | 报工落库 + 状态机 + 触发质检/回传 |
| `mes_erp_callback` | `callback` | Mock ERP 回传 + 写/更新 IntegrationLog |

失败：  
- Consumer 抛错或业务失败 → `RECONSUME_LATER`；  
- 超过重试进 DLQ（可讲 `%DLQ%consumer-group`）；  
- 业务侧：`integration_log.status=failed`，管理端重试或 `@Scheduled` 扫描重试。  

说法：**Broker 重试保证投递，对账表保证业务最终成功可运营。**

---

### Q15. 本地连云上 Docker 的 RocketMQ，遇到过什么坑？

**答（很加分的实战）：**  
NameServer（9876）通了，发送仍超时：NameServer 返回的 Broker 地址是 **Docker 内网 IP（如 172.20.x.x:10911）**，本机连不上。  

解决：`broker.conf` 设置 `brokerIP1=公网IP`，挂载进容器并用 `-c` 启动；安全组放行 **9876 + 10911**。  
环境变量 `BROKER_IP1` 对官方镜像通常**无效**，必须以 conf 为准。

---

### Q16. IntegrationLog 字段怎么设计？重试幂等吗？

**答：**  
关键字段：`biz_type`、`biz_id`、`idempotent_key`（UK，如 `report:{reportId}`）、`target_system`、`status`（待发送/成功/失败/重试中）、`payload`、`retry_count`、`error_msg`。  

重试：同一 `idempotent_key`，成功过则跳过；失败可再发 MQ 或直接调 Mock。保证**回传不会因重试变成多次有效业务副作用**（Mock 侧也按 key 幂等）。

## 五、安全、缓存、前端

### Q17. 权限怎么控？

**答：**  
Spring Security + JWT；接口用 `@PreAuthorize("hasAnyAuthority('ROLE_...')")`。  
例如：派工限 admin/planner；报工限 worker；对账限 admin/planner。  
双令牌：access 短、refresh 长；可讲 access 黑名单/会话校验（若实现了）。

---

### Q18. 看板统计为什么要 Redis？

**答：**  
`GET /api/work-orders/stats` 聚合 7 态数量，管理端轮询会打 DB。  
缓存 Key 如 `mes:stats:wo:status`，TTL 60s；报工成功后删缓存，保证短期内大致准确。  
权衡：**允许秒级延迟**，换 DB 压力下降——看板场景合适。

---

### Q19. 前端报工页要注意什么？

**答：**  
1. 每次提交生成 **UUID** 作为 `X-Request-Id`；连点复用同一 ID 测幂等，换新 ID 才是新单据。  
2. 接受 HTTP 202 /业务码 202。  
3. 轮询直到成功/失败，并展示 `errorMsg`。  
4. 工人只能报自己被派工的任务（后端强校验）。

## 六、数据库与一致性

### Q20. 核心表有哪些？哪些约束最重要？

| 表 | 要点 |
|----|------|
| `work_order` | `erp_order_no` UK；`status`；`version` |
| `operation_task` | `(work_order_id, seq)` UK；`assigned_to`；`version` |
| `production_report` | `request_id` UK；status 0/1/2 |
| `dispatch_record` / `dispatch_audit_log` | 派工与审计 |
| `integration_log` | `idempotent_key` UK |
| `quality_inspection_task` | 报工触发质检 |

最重要约束：`request_id`、`idempotent_key`、乐观锁 `version`——支撑幂等与并发安全。

---

### Q21. 消费时报工成功但发 ERP 消息失败怎么办？

**答（可承认与改进）：**  
理想：本地消息表 / 事务消息 / 事务提交后再发（`TransactionSynchronization`）。  
当前 MVP：同流程内发送，失败则整单消费重试（报工处理有幂等，成功单会跳过）。  
若已成功落库又重复发回调，靠 IntegrationLog 幂等吞掉。  

展示你知道 **分布式事务的边界** 和 **至少一次 + 幂等** 的取舍。

## 七、工程与 Spring Boot 4

### Q22. Spring Boot 4 踩过什么坑？

**答：**  
1. AOP 依赖是 `spring-boot-starter-aspectj`，没有旧的 `starter-aop`。  
2. Jackson 3 包名/配置路径有变（日期序列化配置注意）。  
3. Redisson 要用 **4.6.1+**，3.x 与 SB4 不兼容。  
4. RocketMQ 无官方 SB Starter，用原生 client 手写 Producer/Consumer。

体现「不是只会生成代码，能跟版本演进」。

---

### Q23. 全局异常和统一响应怎么做？

**答：**  
`Result<T>`（code/message/data）；`BusinessException` + `@RestControllerAdvice`；Filter 里鉴权失败也写统一 JSON。  
报工受理用 `Result.accepted`（202）。  
好处：前后端契约清晰，错误可展示。

## 八、场景题 / 追问

### Q24. 如果两个工人被派到同一任务会怎样？

**答：**  
当前模型任务 `assigned_to` 单人；派工会覆盖/按业务拒绝（按你实现说）。  
报工校验：`operatorId` 必须等于 `assigned_to`。  
若要支持多人，需改任务模型（配额/子任务），这是扩展点。

---

### Q25. 如何证明你防住了重复报工？

**答（演示话术）：**  
1. 同一 UUID 连点 5 次 → 库中仅 1 条 `production_report`。  
2. 并发压同一 task → `completed_qty ≤ plan_qty`。  
3. 看日志：幂等返回「已受理/已存在」；Consumer「已成功则跳过」。  
对照 `docs/D28-自测清单.md`。

---

### Q26. 项目亮点你认为是哪三个？

**答（建议固定）：**  
1. **状态机驱动**的工单自动完工，而不是 CRUD 改状态。  
2. **报工三层防重复** + 202 异步受理，能讲清楚每层职责。  
3. **集成对账重试**，体现系统间最终一致，而不是 Demo 只 happy path。

---

### Q27. 有哪些不足？如果再给你两周做什么？

**答（诚实 + 有规划）：**  
不足：Mock ERP/QMS；未开消息轨迹；未做完整 DLQ 告警；多工序在制品核算较简化。  

两周可做：真实 ERP 适配接口、死信监控告警、报工/回传事务消息或 Outbox、简单 APS 优先级规则、E2E 自动化测试。
